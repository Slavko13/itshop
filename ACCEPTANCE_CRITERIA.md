# Критерии приёмки и ручная проверка ITSOFT

Документ определяет, как принимаются логические итерации проекта. Он дополняет `AUDIT.md` и `IMPLEMENTATION_PLAN.md`.

## 1. Правило завершения итерации

Итерация считается завершённой только когда одновременно выполнены условия:

1. Реализован согласованный scope и не добавлена несогласованная функциональность.
2. Миграции выполняются повторно безопасно и не повреждают существующие данные.
3. Пройдены относящиеся к итерации автоматические проверки.
4. Нет известных Critical/High дефектов в изменённом сценарии.
5. Подготовлены точные действия администратора, если они нужны.
6. Подготовлен минимальный ручной checklist с ожидаемым результатом.
7. Описан rollback.
8. Пользователь выполнил ручную проверку и явно подтвердил итерацию.

Без подтверждения следующая итерация не начинается.

## 2. Формат отчёта после каждой итерации

Каждый итоговый ответ содержит:

### Статус

- `ГОТОВО К ПРОВЕРКЕ`, `ЗАБЛОКИРОВАНО` или `ТРЕБУЕТ РЕШЕНИЯ`.
- Краткий итог простыми словами.

### Что сделано

- Реализованные сценарии.
- Что намеренно не входило в итерацию.

### Изменённые файлы и БД

- Путь каждого изменённого/нового файла и назначение изменения.
- Таблицы, индексы, options, post/order meta и версия миграции.

### Автоматическая проверка

- Выполненные команды.
- Количество и результат тестов.
- Непроверенные области и причина.

### Что нужно настроить в админке

- Точный путь меню.
- Значения без публикации секретов.
- Кто выполняет: пользователь или разработчик.
- Как убедиться, что настройка сохранилась.

### Блокеры и решения

- Что именно блокирует работу.
- Какие данные/доступ/решение нужны.
- Можно ли продолжить безопасную часть без блокера.

### Минимальные ручные тесты

- Короткие пронумерованные шаги.
- Ожидаемый результат после каждого сценария.
- Место для результата: `PASS` / `FAIL` и комментарий.

### Rollback

- Как отменить код, миграцию или настройку.
- Какие данные сохранятся и какие могут быть потеряны.

## 3. Общие правила ручного тестирования

- До production проверки выполняются локально и на staging.
- Для платежей используется тестовый магазин ЮKassa и тестовые товары/ключи.
- Реальные лицензионные ключи в тестах не используются.
- Секреты, персональные данные и полные ключи не вставляются в отчёты/скриншоты.
- Каждый тестовый заказ получает пометку `TEST`.
- После исправления `FAIL` повторяется сам сценарий и минимальный regression checklist итерации.

## 4. Минимальные критерии по итерациям

### Iteration 0 — локальная среда и подготовка

Автоматически:

- `docker compose config` проходит без ошибок.
- Контейнеры WordPress, DB и локальной почты становятся healthy/ready.
- Повторный `docker compose up -d` не уничтожает данные.
- Локальная среда не содержит production secrets и не вызывает production integrations.

Ручная проверка:

1. Запустить проект одной документированной командой.
2. Открыть локальную главную страницу — она загружается без fatal error.
3. Открыть `/wp-admin/` и войти тестовым администратором.
4. Открыть товар, каталог, корзину, checkout и My Account.
5. Отправить тестовое письмо — оно появляется только в локальном Mailpit.
6. Перезапустить контейнеры — сайт и данные сохраняются.
7. Убедиться, что production Telegram/ЮKassa/SMTP не получили тестовых обращений.

Для подтверждения нужны: URL локального сайта, способ входа без публикации пароля, результат backup/restore smoke test и список отличий локальной среды от production.

### Iteration 1 — модель склада

Ручная проверка:

1. Активировать новый plugin — активация завершается без ошибки.
2. Проверить версию schema/migration в диагностике.
3. Деактивировать и снова активировать plugin — данные не теряются и таблицы не дублируются.
4. Попытаться добавить одинаковый тестовый ключ дважды через служебный тест — создаётся одна доступная единица.
5. Убедиться, что ключ не доступен через публичный REST endpoint.

### Iteration 2 — склад, импорт и привязка товаров

Ручная проверка:

1. Создать пул и увидеть нулевые counters.
2. Добавить один тестовый ключ — `Свободно` увеличивается на 1.
3. Вставить список с дубликатом и пустыми строками — импортирует только уникальные допустимые ключи и показывает отчёт.
4. Импортировать согласованный TXT/CSV; XLSX — только если включён в scope.
5. Привязать два товара к одному пулу.
6. Выбрать для одного товара AUTO, для другого MANUAL и повторно открыть карточки — настройки сохранены.
7. Пользователь без нужной capability не может управлять складом.

### Iteration 3 — ручная выдача и заказы

Ручная проверка:

1. Создать тестовый оплаченный MANUAL-заказ — issue status становится `Ожидает ключ`.
2. Назначить свободный тестовый ключ из заказа — ключ становится `Выдан`, связь с заказом сохраняется.
3. Повторить действие — новый ключ не списывается.
4. Найти заказ по публичному номеру и email.
5. Проверить один публичный номер в admin и order data.
6. Купить товар при нулевом key inventory — заказ создаётся и ожидает ручную выдачу.
7. Проверить audit trail: actor, operation, order, key, result и время.

### Iteration 4 — ЮKassa и автоматическая выдача

Ручная проверка:

1. Оплатить AUTO-заказ тестовой картой — после `payment.succeeded` назначается ровно один ключ.
2. Закрыть браузер после оплаты — callback всё равно завершает выдачу.
3. Повторить callback — второй ключ не выделяется.
4. Оплатить при нулевом остатке — заказ остаётся оплаченным и получает `Ожидает ключ`.
5. Провести два параллельных заказа при одном ключе — ключ получает только один заказ.
6. Повторить сценарий для двух SKU одного пула — один ключ нельзя получить дважды.
7. Отменённый/неуспешный платёж не выдаёт ключ.

### Iteration 5 — коммуникации и My Account

Ручная проверка:

1. После AUTO и MANUAL выдачи приходит письмо с тем же номером заказа, товаром и ключом.
2. `Повторно отправить` отправляет тот же ключ, counters склада не меняются.
3. Исправить email и повторить отправку — письмо приходит на новый адрес.
4. При остатках 1 и 0 приходит по одному уведомлению, без повторного спама.
5. При недоступном Telegram обязательное email-уведомление сохраняется/отправляется по retry policy.
6. Владелец заказа видит ключ в My Account.
7. Другой пользователь и гость без разрешённого доступа ключ не видят.
8. Проверить login, logout, password setup и mobile registration по подтверждённым дефектам.

### Iteration 6 — checkout и корзина

Ручная проверка:

1. Гость может оформить заказ без обязательной регистрации.
2. Невалидный email блокируется сервером.
3. Несовпадающий повтор email блокирует checkout.
4. Типовая доменная опечатка получает понятную подсказку.
5. Репрезентативные Windows-товары добавляются в корзину.
6. `+` и `-` меняют количество согласно принятому бизнес-правилу.
7. Уменьшение количества не удаляет всю позицию, кроме перехода к разрешённому нулю.
8. Корзина пересчитывается без ручного обновления страницы.
9. Checkout и оплата не имеют блокирующих ошибок на desktop/mobile.

### Iteration 7 — поиск, каталог, UX и mobile

Ручная проверка:

1. Найти товар по `Windows`, `Виндовс`, `Виндоус`, `Винда`, `Win 11` и `Windows11`.
2. Найти Office по `Office`, `Офис`, `Microsoft` и `Майкрософт`.
3. Точное название ранжируется выше синонима, partial и опечатки.
4. Товары выводятся выше статей при одинаковой релевантности.
5. Проверить согласованный порядок Office и SEO-текст под каталогом.
6. Проверить header, cookie banner, сообщения и московское время.
7. На согласованных mobile widths пройти меню → товар → корзина → checkout → аккаунт.
8. На Android проверить ранее неработающую кнопку.

### Iteration 8 — внешние сервисы и выпуск

Ручная проверка:

1. Проверить российский номер в Jivo и зафиксировать страну/результат.
2. Проверить favicon, sitemap, robots/indexing и согласованные замечания Яндекс.Вебмастера.
3. Пройти T01-T10 из технического задания.
4. Проверить существующие товары, старые заказы, пользователей, checkout и стандартные Woo emails.
5. Выполнить migration dry run на свежей копии production.
6. Выполнить малый production smoke test после deployment.
7. Проверить monitoring, журналы ошибок и готовность rollback.

### Текущий минимальный ручной пакет после итераций 7B–8

1. На телефоне открыть `/product-category/microsoft-office/office-2021/`: две карточки в ряд, SEO-текст после товаров, horizontal scroll отсутствует.
2. Нажать burger один раз, раскрыть `Microsoft Office`, перейти в `Office 2021`, закрыть меню крестиком; страница снова прокручивается.
3. Открыть статью `/stati/ustanovka-windows-11-bez-interneta-i-akkaunta-microsoft/`: заголовок, текст и каждое изображение помещаются по ширине.
4. В `/my-account/` проверить формы входа и регистрации, ссылку восстановления пароля и выход после входа.
5. В новом приватном окне принять cookie-banner; кнопки не выходят за экран, после обновления banner не появляется повторно.
6. Открыть `/robots.txt`, `/wp-sitemap.xml` и `/favicon.ico`: все отвечают без ошибки, robots содержит строку `Sitemap:`.
7. Повторить пункты 1–5 минимум на Android Chrome и iOS Safari; эмуляция уже пройдена, но не заменяет физические устройства.

### Extra E — сохранение товара между карточкой и корзиной

1. В новом приватном окне открыть электронный товар и нажать «Добавить в корзину» один раз.
2. Счётчик в шапке становится `1`, кнопка показывает состояние «В корзине».
3. Перейти на `/cart/`: выбранный товар присутствует, пустое состояние отсутствует.
4. Обновить страницу корзины: товар и количество сохраняются.
5. Повторить пункты 1–4 для вариативного физического товара с выбранной вариацией.

### Extra G — редизайн оформления и успешного заказа

1. Добавить электронный товар, открыть checkout и проверить активный шаг `2 — Оформление`.
2. На desktop форма находится слева, состав и сумма заказа — в отдельной карточке справа.
3. Поля, способы оплаты и кнопка оформления соответствуют стилю корзины; выбранная оплата заметно выделена.
4. Для электронного товара адрес доставки скрыт, для физического товара адрес и доставка отображаются.
5. Оформить заказ тестовым способом оплаты и проверить активный шаг `3 — Получение заказа`.
6. На успешной странице видны подтверждение, номер, дата, итог, способ оплаты, состав заказа и данные покупателя.
7. Блок «Что дальше» объясняет выдачу ключа и содержит рабочую кнопку возврата в каталог.
8. На ширинах `393`, `768` и `1280 px` нет горизонтальной прокрутки; на телефоне все карточки образуют одну колонку.

### Extra H — вход, регистрация и личный кабинет

1. Без авторизации открыть `/my-account/`, переключить вкладки входа и регистрации и проверить показ/скрытие пароля.
2. Зарегистрировать временный e-mail; письмо установки пароля появляется в Mailpit, после регистрации доступен кабинет.
3. Запросить восстановление доступа и установить новый пароль по ссылке из Mailpit.
4. После входа проверить адаптивное меню, обзор, счётчики заказов и ключей, последние заказы и данные покупателя.
5. В «Моих заказах» открыть карточку заказа и проверить номер, статус, состав, сумму и действия.
6. В «Лицензионных ключах» проверить, что видны только ключи текущего пользователя; маска, показ и копирование работают.
7. Из другого аккаунта ключ и заказ владельца недоступны.
8. В «Личных данных» сохранить имя и телефон, затем отдельно проверить смену пароля.
9. В «Адресе доставки» проверить обе карточки и пояснение, что электронным товарам адрес не нужен.
10. На ширинах `393`, `768` и `1280 px` отсутствует горизонтальная прокрутка; на телефоне боковая навигация заменяется select.

### Extra I — header и пустая корзина

1. На desktop проверить порядок элементов: логотип → «Каталог» → поиск → пользовательские действия; поиск занимает свободное центральное место.
2. На mobile кнопка «Каталог» скрыта, каталог открывается через burger, логотип и корзина не перекрываются.
3. В новом приватном окне открыть `/cart/`: этапы оформления и старое сообщение WooCommerce отсутствуют, показывается новая карточка пустого состояния.
4. Кнопка «Перейти в каталог» открывает каталог; текст и три преимущества помещаются в карточку без обрезания.
5. На ширинах `393` и `1280 px` отсутствует горизонтальная прокрутка. После добавления товара пустое состояние исчезает, товар и счётчик корзины отображаются.

### Extra J — главная страница и каталог

1. На `/`, `/shop/` и странице категории используются одинаковые дизайн-токены, интервалы и карточка товара.
2. На `/shop/` есть видимый `h1 «Каталог»`; у категории есть её `h1`, ссылка к родителю и описание после сетки.
3. Поиск, сортировка и переход по категориям сохраняют необходимые query-параметры и выдают ожидаемые товары.
4. AJAX-догрузка не дублирует карточки, показывает состояния загрузки/ошибки/завершения; без JavaScript доступна пагинация.
5. Простой доступный товар добавляется из карточки, вариативный ведёт к выбору опций, недоступный товар нельзя ошибочно добавить.
6. На `393 px` каталог показывает две компактные карточки в ряд; категории открываются без обрезания, весь документ имеет `scrollWidth == clientWidth`.
7. Первый экран главной читаем на mobile: заголовок и действия являются HTML-текстом, а не только частью фоновой картинки.
8. Выбранные в ACF категории выводятся с правильными названиями, изображениями и ссылками; изменение настройки видно без правки кода.
9. «Популярные» и «Рекомендуемые» используют единый компонент и не повторяют один товар между секциями.
10. Блок статей не зависит от жёстко заданного ID рубрики и корректно исчезает/сокращается при нехватке записей.
11. На `393`, `768`, `1280` и `1440 px` нет горизонтальной прокрутки, наложений и обрезанных интерактивных элементов.
12. После редизайна проходят regression-сценарии header, поиска, добавления в корзину, checkout и личного кабинета.

## 5. Финальная приёмка проекта

Проект готов к завершению, если:

- все T01-T10 имеют `PASS`;
- нет открытых Critical/High дефектов;
- один ключ невозможно выдать двум заказам;
- повторный callback/resend не списывает новый ключ;
- ключ недоступен постороннему пользователю;
- backup и rollback проверены;
- администратор умеет пополнять склад, выполнять ручную выдачу, исправлять email и повторно отправлять ключ;
- production monitoring и ответственные за внешние сервисы зафиксированы.
## Дополнительная итерация K — дистрибутивы и временные ссылки

### Быстрое демо публичной части

1. Открыть `http://localhost:8080/download/`: видны компактный первый экран, категории и недавно обновлённые дистрибутивы; старого большого баннера нет.
2. Открыть `http://localhost:8080/download/microsoft-office/`: товары находятся сразу под коротким описанием, карточки одинаковые.
3. Проверить поиск, язык, архитектуру, сортировку и вкладки версий. Запрос без совпадений показывает понятное пустое состояние; очистка возвращает карточки.
4. Открыть `http://localhost:8080/distribution/microsoft-visio-2021-professional/`: выбрать вариант по языку/архитектуре и просмотреть пошаговую инструкцию, требования и связанный товар.
5. Уменьшить окно до ширины телефона: горизонтальной прокрутки нет, кнопки не обрезаются, шаги и боковые карточки переходят в одну колонку.

### Проверка админки

1. Войти в `http://localhost:8080/wp-admin/` и открыть «Дистрибутивы» → любую запись → «Файлы и ссылки дистрибутива».
2. Убедиться, что видны название, язык, архитектура, формат, размер, источник, SHA-256, режим, статус, URL/закрытый файл и результат проверки.
3. Для постоянной позиции нажать «Проверить ссылку». На production с разрешёнными внешними запросами должен появиться HTTP-код; локальная конфигурация может блокировать исходящие запросы WordPress, поэтому 18 текущих URL отдельно проверены с хоста и записаны как HTTP 200.
4. Ниже проверить поля «Перед установкой» и «Шаги установки». Изменить текст одного шага, обновить запись и проверить результат на публичной странице.
5. Не менять существующий рабочий файл ради теста. Создать новую тестовую позицию, загрузить небольшой ZIP, выбрать `Защищённая, 24 часа`, статус `Доступна`, сохранить запись.
6. Нажать «Сформировать новую ссылку на 24 часа», скопировать показанный URL и открыть его в приватном окне: файл скачивается.
7. Сформировать ссылку повторно: старая должна показать «Ссылка отозвана» с HTTP 410, новая — скачать файл.
8. Нажать «Отозвать активные ссылки»: последняя ссылка должна вернуть HTTP 410.
9. Отметить тестовую позицию «Удалить позицию» и сохранить запись. Это удалит строку из выдачи; загруженный тестовый файл при необходимости удаляется администратором сервера.

### Условия приёмки production

- Для трёх отключённых ошибочных Office-ссылок получены правильные файлы/URL от заказчика.
- Решено, что скачивается в двух пустых Office 365 записях.
- `ITSOFT_PRIVATE_DISTRIBUTION_DIR` указывает за пределы web-root либо подключено приватное объектное хранилище.
- Проверены ограничения тарифа на размер файла, трафик, PHP timeout и Range-запросы.
- Заказчик подтвердил текущую бизнес-логику: защищённую ссылку вручную создаёт администратор; она допускает повторные скачивания в течение 24 часов.
